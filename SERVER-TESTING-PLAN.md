# Real-server testing plan (final phase)

Status: plan only, 2026-10-20; **updated 2026-10-21: the owner chose to run the original server on their own PC in a firewall-locked setup instead of a VM (section 10, kit in `deploy/host-test`).** Nothing here has been run yet. Everything online so far is verified only against our own mock uLink server (`bridge/ulink/mock-server.mjs`, `tools/check-online.mjs`). This phase proves (or disproves) that the browser port and gateway work against the **original Rust Legacy server**.

## 1. Safety rules

> **Superseded for P1–P8 by section 10 (2026-10-21).** The VM rules below still apply if the VM route is used.

- **No original binary ever runs on the host PC.** The original server (`rust_server.exe`, its Mono/Unity runtime, `librust.dll`, the Steam DLLs) and the original client installer run **only inside an isolated virtual machine**.
- **Executing anything inside the VM needs the owner's explicit go-ahead** for that phase (this plan is not that go-ahead).
- **Network isolation.** The VM gets a **host-only** network adapter and nothing else: no NAT, no bridged adapter, so no internet and no access to the home LAN. The only traffic allowed out of the VM is to the host's host-only address.
- **No host integration.** Shared folders, shared clipboard, drag-and-drop, USB passthrough and 3D-driver "unity" modes are all off. Files go **into** the VM only on read-only ISO images built on the host. Logs and captures come **out** only on a one-way path (a read-only ISO or a virtual disk mounted read-only on the host), and are scanned by Windows Defender on arrival.
- **Snapshots.** Take a snapshot before every phase. After any phase that executed original code, revert to the last clean snapshot before going further. The VM is disposable.
- **Monitoring.** Windows Defender stays on inside the guest. Wireshark on the host's host-only interface records every packet the VM sends, so unexpected traffic (Steam, master servers, the uLink Google Analytics beacon, anything else) is visible and blocked by the lack of a route.
- **Integrity.** Use the server copy we already analysed statically (`RustLegacyServer.zip`, SHA-256 recorded in HANDOFF/analysis). The newly found folder's game files are byte-identical; its real Valve Steam DLLs would try to reach Steam, which the isolated network blocks, so start with our zip's offline Steam emulator build.

## 3. VM build (phase 0)

1. **Create the VM:** Windows guest, 4 vCPUs, 8 GB RAM, 80 GB thin disk, one network adapter set to **Host-only** (VMnet1), 3D acceleration on (only needed for the desktop client).
2. **Install Windows** from the evaluation ISO with a local account. Keep Defender on. Disable Windows Update's network attempts (no route anyway).
3. **Fix addresses:** host-only host = `192.168.56.1` (or VMware's VMnet1 default), guest = static `192.168.56.10`. No gateway, no DNS.
4. **Harden:** confirm no NAT/bridged adapter, no shared folders, clipboard or drag-and-drop; disable the hypervisor's "connect at power on" for any other device.
5. **Tools ISO** (built on the host by me): Node.js LTS installer (official), Wireshark and Sysinternals Process Monitor/TCPView installers (official), our `bridge/` gateway + sidecar + configs, the vanilla patcher and adapter build output, `RustLegacyServer.zip`, and VM runbook scripts.
6. **Snapshot `clean-tools`.**

Exit: VM boots, can reach only `192.168.56.1`, cannot resolve or reach anything else (verified with a ping/DNS test and host Wireshark).

## 4. Topology

```
Host PC (no original binaries)                 VM (isolated, host-only network)
  browser (Edge/Chrome)                          rust_server.exe  UDP 29015 (loopback use only)
  central service + website (Node)  <-- WSS -->  gateway (Node)   ws://192.168.56.10:<port>
  Wireshark on VMnet1                            adapter sidecar (Node, loopback HMAC)
                                                 patched Assembly-CSharp (vanilla adapter) or Oxide plugin
```

Gateway and sidecar run **inside** the VM next to the server, so uLink UDP and the HMAC control channel stay on the VM's loopback, exactly as an operator would deploy them. Only the gateway's WebSocket port is reachable from the host. Central (accounts, join tickets) and the browser stay on the host. `deploy/*.example.json` get a `vm-test` variant for this layout.

**How two-player rows meet: walk-to-meet (2026-10-23).** Every row that needs the target next to the player (`combat.*`, `door.lock`, the P6 `mixed.*` rows) calls `meet()` in `tools/native/gameplay.mjs`. It tries the cheapest way first: (1) already within 2.5 m; (2) with admin rights, `teleport.toplayer` (set `meetTeleport: false` to leave it out); (3) up to `meetRespawns` (3) respawns of the target while it is more than `meetWalkMax` (150 m) away, in case a spawn point lands close; (4) **walk-to-meet** (`tools/native/walk-meet.mjs`). In step 4 the target walks to the player along the original island navmesh (`tools/native/walk-plan.mjs`). That navmesh is the Detour tile set exported by `tools/export_navmesh.py`, baked for a 0.5 m by 2 m agent, so it already leaves out the sea, cliffs, scene rocks and buildings. The planner uses the port's Detour A* and funnel (`browser/navmesh.mjs`), splits the corners into legs of 20 m or less, and checks each leg on the heightmap: no sample below the water line (252.4 m), and no slope over the motor's `slopeLimit` of 65° (`player.json`). Over all original spawn-point pairs the steepest path is about 55°, and almost every path stays under 45°. The movement is ordinary input, nothing the TruthDetector could take for a teleport: the view turns to the next waypoint, W stays held, and Shift is added while more than 20 m from the end. About once a second the walker re-reads both positions. It re-plans when stuck (under 1 m of progress in 3 s), after a jump and a sidestep that back off further on a repeat at the same spot. It also re-plans when it is more than 12 m off its leg, or when the player has moved more than 20 m from the path's end. The last 10 m use `walkTo`. The time budget is `meetMs`, by default 200 ms per path metre plus 60 s (about 7.5 min for 2 km). The row evidence gets `meet`: how it met, the start and end distances, and for the walk the seconds taken, re-plans, stuck count, path length and steepest slope, a progress list (`[seconds, metres left]` every 15 s) and the plans. **Walkers and the TruthDetector (2026-10-23).** A server correction of the walker's own character (`ReadClientMove` to its owner) means TruthDetector rolled a move back: the trace from 0.5 m above the last accepted point hit something the server has on that line (+100 each, no decrement on that move; kick when an accepted move leaves more than 400). The old straight-line `walkTo` walked the same line again after each correction, so every move in flight was blocked again. `walkTo` and `walkToMeet` now hold a `TruthGuard` (`tools/native/truth-guard.mjs`): after a correction they release the keys, let the teleport land (0.4 s), strafe aside 0.7 s and re-plan; while the estimate (+100 per correction, 5 less per second, one per accepted move at sendRate 5) is high they stand still (walk-to-meet's rules since run two-c: see the next paragraph). The walk evidence gets `truth: {corrections, pausedS}`. Every run also writes `moves.json` (both players: sent moves with the browser stamp, spawns, corrections, the disconnect), which `node tools/replay-truth-trace.mjs <run>/moves.json` replays through the TruthDetector model (`tools/truth-detector.mjs`) against the gateway's copy of the server world. A real correction the replay does not reproduce is server-side state the recovered world lacks (a structure, deployable or resource node of the live server).

  - **What a 0 m correction is:** `HumanController.GetClientMove` calls `NetCull.VerifyRPC`, which drops a move stamped earlier than `frameTime − frameDuration − overhead − packet.dropms` (800 ms). On the first dropped move in a run it sends `ReadClientMove(base.origin, …, NetCull.time − info.timestamp)` back to the sender: the server's own position, so 0 m for a bot standing still. Values[3] is the move's age. Every second late move also sends `RS`, a clock resync (`packet.dropclockthresh` 2). Dropped moves are not passed on to other players, so lite bots received about half the traffic (51 → 26 messages/s per bot). The other own-character paths don't fit:

    - Teleports: `UnstickMove`, admin only.
    - Sleepers, airdrops and environment events send no ReadClientMove.
  - **Which delay counts:** `GameBridge.moveStamp` takes its first stamp at arrival, then adds the browser's own gaps and only ever drops to the arrival time. So a move is dropped when the browser → server delay is about 0.8 s worse than that session's best. A stall on the server's main thread alone does not cause this: the first uLink update after a stall gets `frameDuration` = the stall (`NetCull.TimeMeasureStart`, `lowestSafeTimeInMillis`), which widens the window by the same amount. Console commands are not checked by `VerifyRPC`, so the 9 s probe round trips were real delivery delay.
  - **The delay was also outside the game server:** at 13:05:57–13:06:08, join tickets took **0.4–2.1 s** (normally 0.12–0.14 s), and ticket → approval took up to 3.7 s (normally 0.45 s).     1. **The path between the test PC and the VM, the PC included: most likely.** All 20 bots ran on one shared PC over one connection, and the PC was at 31 of 32 GB two minutes before.     3. **A stall in the gateway's event loop: unlikely.** Its console log is written synchronously on Windows, but a gateway stall cannot slow central's tickets, and CPU was 4 %.
