# Rust Legacy browser port: fidelity and next steps

The objective is the original Rust Legacy experience in a modern browser. Original assets, world placements and recovered behaviour are the source of truth. Do not add invented survival systems, substitute maps or present temporary explorer controls as the original game's movement. The browser renderer and transport adapters replace incompatible engine/platform infrastructure; this does not make the existing legacy executable browser compatible.

## Website (2026-10-20)

Phase 1 of the website is done (spec `docs/superpowers/specs/2026-10-20-website-design.md`): title-screen homepage with the original menu music, accounts (email/username/password plus Steam/Discord with a chosen username), server browser and shareable server pages, The Island (modern map built from the scene, aerial render of the port, classic layer pending the owner's image), wiki generated from the original game data plus staff articles, updates, how to play, owner tools and the restyled admin console. Checked by `npm test` and `npm run test:site` at desktop and phone widths. Forum is phase 2.

Materials now export every texture slot, their floats and colours, and the ShaderLab shader name.

**Sea level corrected:** the original water is the `Tile` object with `FX/Water4` at **252.4 m** (50 km plane). The earlier explorer placed water at 0.15 m, which showed seabed as dry land. The browser takes height and extent from that exported object and renders it with a port of the compiled FX/Water4 program (`browser/water4.mjs`, see the sky/sea section below). Swimming rules are not ported.

The paragraphs below describe the earlier server-scene import; their counts are superseded by the figures above.

`tools/export_scene.py` statically parses the original scene and dependencies. It resolves asset-local and external pointers, parent transforms and Unity's static-batch subset references. Local geometry reflects Z; matrices are converted with H * world * H. Combined static geometry uses its batch root (world space for null root), while original collision meshes retain their object's world transform. The original visible geometry is not re-applied to each object's transform.

The source has 901 MeshRenderers: 458 are enabled in active hierarchies, and 443 are initially disabled or inactive. All 458 enabled/active objects resolve without missing mesh/material dependencies. The renderer draws 421 world objects (427 submesh parts) and omits 37 parts using engine-effect or context-marker materials. Clouds, atmosphere, sun, water effects, context sprites and depth-writing effects require their own shader/runtime ports. They must not be displayed as opaque diffuse surfaces. The disabled/inactive set is retained in the export report; scripts that activate it are still to be mapped.

Recovered content includes original warehouses, hangars, bunkers, apartments, walls, fences, pipes, containers, barrels, roads and rocks. Original building names/IDs provide camera destinations from their actual geometry bounds. This navigation is a development aid. Startup now shows the recovered warehouse compound.

Original textures and UV transforms are used. Three.js lighting/material response remains an approximation: original shaders, normal maps, original lighting, transparency behaviour and visual parity are unfinished. Tree rendering is bounded nearby instancing, not original LOD behaviour.

## Collision and movement integration

The export contains 273 active solid MeshColliders and 148 BoxColliders, with source IDs, object layers and full matrices. They are now connected to browser walking through a spatial index of 124,796 non-degenerate triangles, including source boxes converted to triangles. Trigger/disabled/inactive colliders are excluded. Three active mesh colliders have null original mesh references; these are recorded explicitly instead of replacing them with guessed visual geometry. Tree collider prototypes live in a separate scene and are not yet instantiated.

The browser motor supports acceleration, direction-dependent speed, sprint/crouch curves, jumping, gravity, wall sliding, floor/roof/ceiling collision, stepping and blocked standing beneath low ceilings. It uses recovered player settings, not the earlier explorer speed. Tests include original warehouse roof geometry, walls, stairs, ceilings, low openings, steep terrain and source speed limits. This is a partial adaptation of CCMotor to a browser capsule solver, not a verified reproduction of Unity's PhysX controller. P3-14 (2026-10-20, `tools/export_physics.py` -> `physics.json`, `tests/motor-parity.test.mjs`, `npm run test:motor`): the CCTotem pole is ported from `CCTotem.Configuration` (5 skinned figures, 1.3..2.08 m, created contracted on spawn/teleport, height changes at HumanController crouchSpeed 1 m/s, the top stops at ceilings = partial stand + crouchBlocked); the solid hull is radius + skinWidth (0.45 m); the eye follows `Crouchable.Smoothing`; collisions use the layer-16 "Character Collision" row of the original layer matrix (debris 18, hitbox 17, RayOnly 21, ragdoll 27, other characters 16 never block; per-prefab solid collider layers); CCPusher (28, all on scene MovingDoors) pushes at 40 x dt while grounded, and a pusher door moving into the player passes into it as in PhysX until the push clears it; CCMotor moving platforms (PermaTransfer: carried position/yaw, platform velocity kept on leaving); walking off a ledge drops CCMotor's ground push (num3) once. PlayerPusher (10) is a no-op in this build (needs a layer-16 GameObject with CCMotor, which lives on the layer-0 totem pole, and CCMotor.DoPush is empty). Still approximate: full air-input/landing/jump-buffer rules and the grounded too-steep sliding branch of ApplyInputVelocityChange. Doors remain in their static imported pose. Terrain contact currently uses the rendered 513² grid rather than the full 2049² source grid.

## Original movement: static code evidence

Read the target bytes using our own `StaticIl` PE/CLI reader; no supplied assembly was loaded or executed. Evidence files under ignored `analysis/`:

- `original-movement-il.txt`: `HumanController`, `CCMotor` and nested movement/jump code from client Assembly-CSharp.dll.
- `original-control-configuration-il.txt`: `HumanControlConfiguration` and `CharacterCCMotorTrait`.
- `facepunch-movement-il.txt`: Facepunch.Movement.dll, primarily animation state/matrix code. The library name alone is not evidence that it implements the character motor.

Observed code defaults (not yet verified effective player-prefab/runtime settings):

| Source method | Observed default |
| --- | --- |
| CCMotor/Movement::get_init, method 0x060018b7 | Forward, sideways and backwards speed 3; ground acceleration 30; air acceleration 20; gravity 10; max fall speed 20; air input velocity ratio 0.8 |
| CCMotor/Jumping::.cctor, method 0x060018bc | Jump enabled, baseHeight 1, extraHeight 4.1, steepPerpAmount 0.5 |
| HumanControlConfiguration::.ctor, method 0x06000a71 | Sprint curve (0,0) to (0.4,1); crouch multiplier curve (0,1) to (0.4,0.55); landing penalty curve (0,1), (0.25,0.5), (0.75,1); sprintScalars (0.2,1) |

`tools/recover_player.py` now resolves the actual `player_soldier`/MalePlayer prefab and its Male -> Human -> Default trait inheritance. The serialized settings override the code defaults above: forward/sideways/backwards speeds **4 / 4 / 3**, ground/air acceleration **100 / 20**, gravity **35**, terminal fall speed **80**, jump base/extra height **1 / 0.5**. The source controller has radius **0.405**, slope limit **65 degrees**, step offset **0.5**, skin width **0.045**; the totem height range is **1.3..2.08**, and the player's original eye transform is **1.647596 m** above the player origin. These values and source IDs/hashes are exported to `browser/assets/recovered/player.json`. Two unrelated sample FPS/third-person controllers were identified and excluded.

Unity curve interpolation preserves recovered tangents. Fly mode remains a development aid. Walk mode now uses the adapted motor, with the limitations described above; full original gameplay is not claimed.

## Local two-client transport test

`npm.cmd run test:multiplayer` runs a disposable loopback test using two isolated Edge browser contexts and our own `session-server.mjs`. Server-side movement uses the same recovered settings, collision geometry and adapted motor as the browser. Clients send bounded, sequenced input; they do not supply authoritative positions. The test verifies that the other client observes movement, client position fields are ignored, invalid input/auth/cross-origin requests are rejected, stale input stops movement and disconnect removes a session. Session credentials are ephemeral and not written to evidence.

This is an HTTP transport harness with protocol label `local-port-test-v1`, not an implementation of the original uLink/1069 wire protocol. Its same-origin test pages isolate transport from GPU rendering. Full scene rendering is checked separately. The public explorer has no connected-peer rendering or multiplayer button yet. Peer models, original authentication, legacy-server compatibility, inventory replication, survival/combat and network corrections remain unimplemented.

The user confirmed no isolated test host is available. The earlier prohibition on running supplied game/client/server binaries on this PC remains in effect. Our own browser/server code can and has been tested locally. Original-server compatibility still needs a permitted test environment or a later explicit change to that boundary.

## Decompiled original code (ILSpy)

`node tools/decompile.mjs` (requires `dotnet tool install -g ilspycmd`, ILSpy 11.1) decompiles the client and server `Assembly-CSharp`, firstpass, UnityScript and Facepunch.* assemblies to C# projects under ignored `analysis/decompiled/{client,server}/`. ILSpy reads metadata and IL statically; nothing is loaded into a CLR or executed. All 24 assemblies decompiled; only 2 of ~1,280 server Assembly-CSharp files carry decompiler warnings. This replaces reading raw CIL with `StaticIl` for porting work: use the decompiled C# as the reference for each gameplay system, and keep citing class/method names. RustProtect.dll was deliberately not decompiled into the port path; it is protection/network code, not gameplay. REA (`rea-agents@6.5.0`) is also registered for Claude Code for static PE/CLI identity and member inspection.

## Original doors (implemented)

`tools/export_scene.py` exports all 32 active MovingDoor components: serialized settings, local TRS, parent world matrix, the GameObject subtree and their original sounds from `audioclip.000.unity3d` (Ogg Vorbis, e.g. `garage_door_open`/`garage_door_shut`). Door render parts and colliders are tagged with their door. `browser/doors.mjs` is a line-by-line port of decompiled `BasicDoor`/`MovingDoor`: RunFlags (start opened, reverse rules, waits-for-target), the Opening/Opened/Closing/Closed state machine, `StartOpeningOrClosing` remaining-time maths (reversal mid-motion is continuous, with original integer-millisecond truncation), `UpdateMovement` (pivot rotation, `smooth` SmoothStep, `slerpMovementByDegrees`, ABS flags, rotation-first), `IdealSideForPoint` so reversible doors open away from the opener's eyes, `ContextRespond_OpenCloseToggle` including its original millisecond-vs-`minimumTimeBetweenOpenClose` comparison, and client `ContextText` ("Open"/"Close" only while at rest).

Doors with startConfig bit 1 start open, as in `Awake`. Door colliders (29 boxes, 3 original mesh colliders) are moving bodies outside the static octree; they follow each door's displacement from its source pose, so walking is blocked by closed doors and frees up when they open. Interaction follows client `ContextProbe`: an eyes ray of the recovered `CharacterContextProbeTrait._rayLength` (3 m); the first solid hit decides the target (all exported static layers are inside the original raycast mask). The original default bind `Use E` with `Context.kQuickTapMillisecondLimit` (300 ms) issues the quick toggle. Sounds play positionally with `SoundPool` defaults: linear rolloff, volume 1, min 5 m, max 20 m.

Tests: `tests/doors.test.mjs` checks every door's computed closed pose against its exported collider transform (validating the Unity→browser conversion), timing/events/reversal, roll-up pivot and slerp travel, side-dependent hinged opening and moving collision. The Edge check aims at a garage door and a hinged door, taps E, and captures closed/open screenshots (`analysis/browser-qa/door-*.png`), which were visually reviewed.

Not yet ported: the hold-E context menu (`ContextQueryMenu`: Open Door/Close Door, plus lock actions that only apply to player-deployed doors with `LockableObject`), NavMeshObstacle carving (Ore2 only; obstacles are avoidance cylinders, door ones enabled while closed), `ContextSprite` world hint sprites, and door state in the multiplayer harness (the server builds door bodies in their source pose). FixedUpdate-flagged doors are sampled per frame rather than at Unity's fixed step. **Update (verified 2026-10-22):** the hold-E menu (`context-ui.mjs`, `locks.mjs` `doorMenu`: Open/Close Door plus the lock actions on owned deployed doors), NavMeshObstacle avoidance and ContextSprite hints are ported; door state online comes from the server.

## Original survival: metabolism, bleeding, eating and medical items (implemented)

`browser/survival.mjs` ports decompiled `Metabolism` and `HumanBodyTakeDamage`. Values come from the recovered player prefab (`tools/recover_player.py` now exports its HumanBodyTakeDamage: 100 health, 8 s bleed interval) and CharacterMetabolismTrait (2 s self-tick).

- **Calories:** start at 1,250, max 3,000. Burn per hour is 300 + activity × 2,700, with activity easing toward 0 still, 0.15 crouch-moving, 0.4 walking or 0.9 sprinting (set from HumanController.ServerFrame every 200 ms). Each melee swing costs `caloriesPerSwing` × 0.8–1.2, and swings take twice as long at zero calories.
- **Starvation:** 10 hp per minute at zero calories.
- **Regeneration:** 10 hp per minute at 5 calories per hp, only when not bleeding, not irradiated and at least 10 s after the last damage.
- **Poison:** a vomit 5 s after poisoning and then every 10 s (−2 hp, −100..199 calories, −1 poison), plus 10 × poison hp per minute.
- **Radiation decay and anti-rads** are ported; the 12 original RadiationZones now supply exposure (see environment milestone below).
- **Water** is tracked but never consumed. Rust Legacy has no thirst, and the port keeps it that way.
- **Bleeding:** HumanBodyTakeDamage starts bleeding from melee/bullet hits once health loss exceeds 20%. A hit of 25% or more of max health always bleeds; 15–25% has a Random.Range(0,2) chance and 5–15% a Random.Range(0,3) chance. Bleed level is 15% of the damage, applied every 8 s and dropping by 0.2 per bleed. Physical hits cancel heal-over-time; CheckLevels heals 3 hp/s from heal-over-time.
- **Eating:** ConsumableDataBlock.UseItem runs from the right-click item menu, labelled Eat/Drink/Consume by the original GetConsumeMenuItem rule, with a 3 s consume cooldown and calories capped at the remaining space. Raw Chicken Breast: +80 calories, −10 health, 3 poison. Cooked Chicken Breast: +500 calories, +2 health over time.
- **Medical items:** BasicHealthKitDataBlock.UseItem (Bandage, Small Medkit +40, Large Medkit +100) stops bleeding and heals over time, with a 5 s cooldown. Use them from the right-click menu or the belt number key. As in the original, they do nothing at full health even while bleeding.
- **HUD:** shows health, calories, Bleeding, Poisoned and rads; the earlier death/respawn flow resets these.

Cooking is now ported with deployables (below); time of day, radiation sources and armour are now connected. **Update (verified 2026-10-22):** the RPOS vitals plaques (`hud.mjs`), item tooltips (`tooltip.mjs`), the vomit sound (`audio.mjs`) and eat/use sounds (`item-events.mjs` UsedSound) are ported. The BandageDataBlock hold-to-use variant stays unported (no shipped item uses it).

The island terrain is a heightfield outside the octree, so placement rays march it separately.

## Original building: structures, hardpoints and placed doors (implemented)

`browser/structures.mjs` ports StructureMaster, StructureComponent.CheckLocation, StructureComponentKey, StructureComponentDataBlock (CheckBlockers, DoAction1) and StructureComponentItem.RenderPlacementHelpers from the decompiled sources; 16 structure items (wood and metal foundation, pillar, wall, doorway, window, ceiling, stairs, ramp).

- **Grid:** pieces live in their master's space on 2.5 m (XZ) and 4 m (Y) steps. Keys round halves to even like Mathf.RoundToInt. The first foundation creates the master and fixes its material; others must match.
- **Placement preview:** eyes ray of 8 m (4 m for ceilings); foundations, ceilings and ramps aim 3.5 m below the hit point; for each master whose bounds (piece colliders + 5 m) the ray meets within 10 m, the point snaps to its grid with the master's rotation times the player's 90-degree turn (right click or mouse wheel). A new foundation is valid only on terrain, away from other masters' bounds; the server path refuses it when the ray meets any structure. Foundations within 5 m (2D) of a spike wall and anything in a NoPlacementZone are blocked.
- **CheckLocation:** foundations beside an existing one (5 m along its local X or Z, same height) with terrain within 3.5 m above the base; pillars on a foundation top (local y 4) or another pillar; walls, doorways and windows between pillars at both ends (±2.5 m along the piece's right); ceilings and stairs with pillars at all four corners; ramps on a valid foundation spot or above a ceiling/foundation. Occupied cells are refused.
- **Hardpoints and carriers:** doorways, window frames, the wood shelter and the gateway expose their Hardpoint children; doors, gates and window bars (requireHardpoint, HardpointPosRot) take the first hardpoint of their type within 3 m of the ray hit. Deployables remember their TransCarrier and are destroyed with it.
- **Placed doors:** use the scene MovingDoor port with the prefab's settings and original open/close sounds.
- **Damage:** ProtectionTakeDamage armour — pillars and walls ignore melee (200), walls take explosive damage, wooden doors take 10% of melee. Weight links in the original only decide which pieces decay; there is no collapse.

Not ported: structure decay (2–5 days delay, then damage over 6–72 h), code locks, explosives, repair, the original pulsing placement material, ownership checks and persistence.

## Original combat: firearms, bows, grenades, explosives and armour (implemented)

`browser/combat.mjs` ports the decompiled client and server weapon code. All stats come from the recovered datablocks (e.g. M4 30–40 damage, 0.125 s, 24 rounds of 5.56, 140 m; Shotgun 12 pellets of 15 within ±5 degrees, 30 m; Bolt Action Rifle 60–65, 250 m, 2.2 s).

- **Firing:** WeaponItem timing (deployLength, sprint lockout, semi-auto edge detection, fireRate), dry fire, reload (ammo moves into the clip immediately; firing waits reloadDuration), recoil impulses eased over recoilDuration and reduced by aiming/crouching. Bullets travel straight down the eyes ray (no spread; shotgun pellets spread by Euler angles). Server damage: Random.Range(min, max) bullet damage, silenced ×0.8, headshots ×8 on AI and ×3 on players (no hitboxes yet). Condition loss per shot and broken-weapon lockout. Gunshots alert wildlife (HearDanger, 20 m at the shooter, 10 m at the hit).
- **Bows:** draw on hold (drawLength), tire after 1 s, cancel after tooTiredLength or an early release, fire on release using an arrow from the inventory. ArrowMovement flies at arrowSpeed and pitches down 5 degrees/s; a hit on anything with TakeDamage deals 75 melee damage.
- **Grenades:** ThrowableItem pin/hold/release (1.25 s minimum), thrown at a fixed 20 m/s by the server; TimedGrenade explodes after 3 s with the recovered radius 6 m and damage 120.
- **Explosions:** ExplosionHelper surfaces (collider bounds within the radius, linear falloff to the bounds centre, ×0.1 when blocked, one per object) for grenades and the explosive charge (TimedExplosive: 5 s fuse, 3 m, 600; its carrier takes the full damage). Structure armour decides the result: walls take explosions in full, pillars are immune.
- **Armour:** equipment slots 36–39 with the original slot flags; worn armorValues summed into ProtectionTakeDamage (×(1 − armour/200) per damage type).
- **Assets:** weapon sounds (fire, dry fire, reload, draw/fire/cancel arrow, pull pin, grenade bounce, charge tick), the arrow and grenade models and the Explosion1 effect (six Shuriken systems, light flash, sound).

Not ported yet: held weapon viewmodels/world models and animations, muzzle flashes, impact effects/decals, the hit notification HUD, hitboxes/headshots, weapon mods (silencer, holo/laser sight, flashlight), the Supply Signal airdrop, arrow pickup and the hand-held torch.

## Original environment: time of day, night cold and radiation (implemented)

`tools/export_scene.py` now recovers the active server scene's TOD_Sky parameters and all 12 RadiationZones. `browser/tod.mjs` ports the decompiled `EnvironmentControlCenter.Update`, `TOD_Sky.SetupSunAndMoon`/`SetupLightSource`, `RadiationZone.GetExposureForPos` and `Radiation.CalculateExposure`; `main.mjs` connects them to the renderer and player survival.

- **Clock:** starts at the recovered noon, 18 February 2013, equatorial latitude/longitude. `env.daylength=45` and `env.nightlength=15` scale a full 24 game hours, chosen per frame by IsNight; they do not mean a 45-minute daylight half plus a 15-minute night half. Calendar rollover and moon phase follow EnvironmentControlCenter. A one-second simulation of the initial noon-to-noon cycle takes about 2,044 real seconds.
- **Sun/moon:** recovered orbital calculation, LerpValue, ambient colour, light colour/intensity, minimum light height and moon phase. The dome rotation is applied without its scale. Float underflow in Mathf.Exp must be preserved: IsNight tests LerpValue == 0, and JavaScript double precision alone makes twilight last too long. Other arithmetic uses JavaScript doubles, so this is not bit-for-bit Unity parity.
- **Cold:** Metabolism receives IsNight. An unwarmed player has coreTemperature −1 and burns 1,500 extra calories/hour. Cold armour adds armour × 0.05 toward zero; a lit HeatZone marks warmth at +1. The HUD shows Cold/Warm, clock and rads.
- **Radiation:** exposure sums active zones at the character origin, with a linear centre falloff where strongerAtCenter is set, then scales by 1 − clamp(radiation armour / 200). HumanController's 200 ms server-frame equivalent adds exposure × elapsed seconds / 60. Existing Metabolism handles decay, poisoning above 500 rads and anti-rad items. Developer fly/dead intervals do not accrue exposure into a later walk frame. Zone membership uses a point-in-sphere check, approximating Unity trigger overlap at the character boundary.
- **Water:** HumanController's water-line death check now applies to the player as well as wildlife. It is lethal at/below 252.4 m; no swimming rules have been invented.

World lighting still uses Three.js lights/materials scaled by the TOD light colour, intensity and ambient. Shadow fidelity, Geiger audio and the original radiation/cold HUD remain unfinished. These systems run locally; native server sky synchronization is not implemented.

`tools/export_sky.py` statically exports the client RustSky (TOD_Sky, TOD_Animation, TOD_Resources meshes/materials/textures), the in-game Scene Camera prefab (TOD_Camera, far clip 6000), RenderSettings fog, PlayerSettings colour space (gamma) and RustWater (WaterBase, PlanarReflection, WaterColor, Tile grid, Utility/WriteZ plane) to `browser/assets/recovered/sky/` (gitignored). - **Sky (`browser/sky.mjs`, rules in `browser/sky-model.mjs`):** Space/Moon/Atmosphere/Sun composited in one draw on the original Icosphere (per-vertex SampleAtmosphere and star UVs as in the original programs, sun quad and moon sphere intersected per pixel, moon phase lighting), plus the original Half_Icosphere Cloud Layers (Bumped) draw with its own tangents, noise/normal textures and TOD_Animation wind scrolling. Gamma-space maths; the canvas receives the original gamma values (pixel-checked against SampleAtmosphere on the GPU). Dome radius 0.95 x 6000 m around the camera.
