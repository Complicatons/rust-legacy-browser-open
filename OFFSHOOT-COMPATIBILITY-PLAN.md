Can our browser and desktop clients join the servers run by other Rust Legacy communities? This plan answers that for each community the owner listed, says what each needs, and lists the remaining checks.

Next gate: the first VM test with the real game (DESKTOP-LAUNCHER-PLAN.md next steps). Players need a website account and can create one in the loader.

> **29 October 2026: Fougerite servers need the IL patcher, not a plugin.** Researched Fougerite's own public source (github.com/Notulp/Fougerite — the framework's real open-source repository, never the RustBuster copy bundled in the survey). ## What all of them have in common

Every community below runs the same 2015 Facepunch server (protocol `1069`, uLink over Lidgren UDP). Our gateway already speaks that protocol ([ULINK-PROTOCOL.md](ULINK-PROTOCOL.md), `bridge/ulink/`) and passes the P5 matrix against the original server. Gameplay traffic is therefore not the problem. Server-side plugins (Oxide, Fougerite, Magma, kits, `/home`, and so on) run on the server, so our players get them automatically.

The difference between communities is the **login**. Our gateway sends `writeRustLogin`: protocol, mode, a 64-bit user id, a name, and a ticket blob. The ticket is our `RLBA`/`RLBD` envelope, never a Steam ticket. A server then does one of three things:

1. **Stock Steam check** (`AuthorisationRoutine` → `SteamServer_BeginAuthSession`). The envelope fails, so the player is denied unless the server runs our adapter (Oxide plugin `adapter/RustLegacyBrowser.cs` or the vanilla patcher).
2. **Steam check disabled or emulated** (servers built for cracked/LumaEmu clients). We do not build anything to fit these on the client side: our side of compatibility is the same adapter as type 1, installed by the owner. We never stand in for Steam sign-in to slip a player in.
3. **The community's own login** (account token, client handshake, client anti-cheat). The server refuses anyone who doesn't present that community's proof. Only that community can let us in.

## Rules we keep

- **Compatibility is server-side only, with the owner's written OK.** The one route is: the server owner installs our plugin/adapter and admits players who signed in on our website. Nothing on the player's PC stands in for Steam, for a community's own sign-in, or for its anti-cheat on a server that has not installed our adapter — not even where it would be technically possible, and whatever the server does. The loader's `steam_api` proxy (un-paused 24 October) is the desktop half of our adapter's own sign-in: it arms only after that server's gateway admitted the player, and its envelope is accepted only by our adapter. The survey (below) only identifies each server's version and setup so our plugin fits; it is never used to copy anyone's sign-in or anti-cheat.
- Where a community's servers need their own proof, the route is to ask the operator: they install our adapter, or they accept our signed envelope next to their own login.
- Downloads and analysis of third-party clients happen only on a throwaway VM that is deleted afterwards. Nothing downloaded is run. Only text (listings, decompiled C#, strings) comes back to the PC.

## Owner direction (2026-10-23)

> "for each one of these offshoots we should offer a viable way to turn their server "browser ready" and we make our own game loader where people have to login using login from our website, once logged in they can click play on the loader and rust will load, anyone trying to join our server without logging into the loader successfully cannot join. We need to make it easy for those servers to update to make them browser ready or they can use our software we're going to make."

That gives three parts. The first is built; the other two are designed here.

### 1. Our servers: launcher only (built)

Both adapters now have a **`LauncherOnly`** switch: the Oxide plugin's config key `LauncherOnly`, or `LauncherOnly=true` in `cfg/rustlegacybrowser.cfg` for the vanilla patch. With it on, a login is admitted only when it carries a website-issued envelope: `RLBA` from the browser gateway or `RLBD` from the desktop launcher. The sidecar still checks every envelope (one use, 30 s, Ed25519 pass from central). Every other login is refused with the client's own "Authorization failed" message (`NetError.Facepunch_Connector_AuthFailure`), and the server log records the refused user ID. That includes real Steam, LumaEmu, RustBuster and any other community's client.

- Off by default, so community servers that install the adapter keep their existing players.
- Our own servers turn it on. The desktop launcher's window, `steam_api` proxy and launch profile are built and tested (DESKTOP-LAUNCHER-PLAN.md "Built: window, host, proxy, launch profile", 2026-10-23; back in scope after the 24 October decision, with sign-up in the loader, hardware ID and a per-user installer added that day), but it has not met the real game yet and is unsigned. Until its VM gate passes and it ships, a LauncherOnly server has **browser players only**; after that, desktop players join it through the loader.
- This is stricter than DESKTOP-LAUNCHER-PLAN's proposed `requireLauncherForLinked`, which only locks characters already linked to an account. Both can exist: LauncherOnly for our servers, the per-character lock for community servers that keep native players.
- Tests: `tests/launcher-only.test.mjs` pins both adapters (off by default, same refusal). Oxide compile-check and vanilla Release build: 0 errors. Not yet run on a server; the next VM matrix run should add a "LauncherOnly on: native client refused, browser admitted" row.

The loader the owner described is the desktop launcher already designed in DESKTOP-LAUNCHER-PLAN.md: sign in with the website account (password, or a device code for Steam/Discord accounts), pick a server, press Connect, then Launch. It runs the player's own game copy through a `steam_api` proxy that hands the server an `RLBD` envelope. A heartbeat keeps the session alive, and the player is kicked within about 60 s if the launcher is closed. The launcher works on any server that is browser ready (part 2), not only ours.

### 2. Browser ready: what another community installs

"Browser ready" means the server accepts website envelopes next to its own players. It always takes the same three pieces:

1. **The adapter** for the server's mod framework (table below), with `LauncherOnly` off so their own players keep joining.
2. **Gateway + sidecar** (Node, from our kit): the gateway speaks WebSocket to browsers and native uLink to their server on the same machine. The sidecar holds the identity map.
3. **Enrolment** with our website: the operator registers the server on the site and gets its gateway credential (`13-Enrol-Gateway` today, a wizard step in the host app). The server then shows in our server list and the launcher's list.

### 3. Or run our software: the host app

For an operator who would rather not wire this up by hand, the host app (HOST-APP-PLAN.md: Windows service, setup wizard, dashboard, updates) installs and supervises everything above. Today it only accepts the stock server, checked against `deploy/host-test/settings.json`. To take a community's existing server it needs:

- an **"attach existing server" wizard step**: detect Oxide (`oxide/` folder, `Oxide.Core.dll`), Fougerite (`Fougerite.dll`, patcher once a sample DLL confirms the hook site) or stock (hash match), and install the matching adapter; **built 2026-10-29** (work item 5), Fougerite detected and refused until this item lands;
- **framework-aware hashes**: record the operator's own modded `Assembly-CSharp.dll` hash at attach time instead of refusing it, while keeping the patcher's allowlist for the vanilla patch;
- **their plugins left alone**: the app supervises the server process and our parts, and never touches their plugin folders beyond our one adapter file;
- **updates**: our update channel already replaces our parts and restarts only what changed; the adapter file is included so a new LauncherOnly/security fix reaches every browser-ready server.

**Design worked out from our own decompiled reference (`analysis/decompiled/server/Assembly-CSharp/ConnectionAcceptor.cs`, `uLink/BitStream.cs`, `uLink/NetworkPlayerApproval.cs`), built and verified 2026-10-29 against a from-scratch synthetic fixture (real VM round against the genuine Fougerite file still pending — see below):**
- In the *original* method, `ClientConnection` is never passed in — it is built fresh, inline: `new ClientConnection().ReadConnectionData(approval.loginData)`. Our stock patch's existing design (find `m_Connections.Add` and reuse the connection *variable* already sitting above it) is one way to reach that object, but it is not the only way, and it is the fragile part: it assumes the method still does that construction inline, which Fougerite's build no longer does.
- `NetworkPlayerApproval.loginData` is a `public readonly BitStream` **field** (confirmed in the decompiled source), and `BitStream.ReadConnectionData` reads it sequentially (`ReadInt32`, `ReadByte`, `ReadUInt64`, `ReadString`, `ReadBytes`) — reading it a second time would continue from wherever the first read left off, not restart, so two callers can't safely share one `BitStream` instance. But `BitStream` also exposes `public byte[] _data` (a getter) and `public readonly bool isTypeSafe`, and has a `BitStream(byte[] data, bool isTypeSafe)` constructor — so we can build our **own, independent** `BitStream` over the same underlying bytes (`new BitStream(approval.loginData._data, approval.loginData.isTypeSafe)`) and read *that* without ever touching `approval.loginData`'s own position.
- That means the fix does not need to recognise Fougerite's shape at all, or locate anything inside it. Insert our check **unconditionally at the very start of the method**, for every build, stock or patched: construct our own `ClientConnection`, from our own fresh `BitStream` copy, call `Hooks.OnUserApprove(connection, approval, this)`, and `return` if it says so; otherwise fall through into whatever the rest of the method already does (the original inline logic on a stock build, Fougerite's own dispatch on a Fougerite build), completely unaffected, because `approval.loginData`'s own read position was never touched. This replaces the stock patch's current `m_Connections.Add`-search with something that no longer depends on recognising any particular build's internal shape at all — simpler *and* more robust for stock servers too, not just a Fougerite special case. The sidecar already re-checks bans/whitelist itself for envelope logins (`bridge/adapter.mjs`), so running before the native checks costs nothing.

## Answer to "without fail"

Not possible for every server, and we do not try to make it so from the client side. A server decides who it lets in, and our only route is the owner installing our adapter and admitting website-signed-in players — with their written OK. What we can promise is that the game itself (protocol, world, combat, plugins) works the same once a server the owner has set up lets the player in.
